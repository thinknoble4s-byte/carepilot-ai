1. Scope and principles

This design implements MVP Golden Path Steps 0–9 and the prototype v7.2 screens: Workspace, Patient journey, Intake and verification, Care Plan, Needs my decision, Audit trail, Rules, Programme and Performance indicators. It follows the locked agentic architecture: the LangGraph agent, gap rules G0–G6, the autonomy policy and the four-actor audit ledger.

Scope of this build. All patient data is synthetic. The WhatsApp channel and the hospital record (EMR) are simulated. The Sarvam and Vertex AI calls are real. The demo is reachable by outside reviewers at a public HTTPS URL, with one demo login per role.

  1. Safety is enforced in code and state, not in prompts. Consent, pause, agent-off and open-handover checks all run in one send-guard inside the database transaction.
  2. Each AI does one job. Sarvam handles Indian-language input and output. Gemini plans and structures, but only within an allow-list. Neither model writes text a patient receives: patients only get approved templates.
  3. Safe path on any doubt. A health flag of YES or uncertain, a timeout or an error opens a handover. If Gemini fails, the agent falls back to the rule table's default action.
  4. Pay per use, scale to zero. The only always-on AWS costs are RDS and a tiny NAT instance.
  5. India residency. AWS runs in ap-south-1 and Vertex AI uses the asia-south1 regional endpoint, never the global one. Chat models only see tokenised text.
  6. Same actions for agent and human. The agent has no private tools, and every action writes an audit entry in the same transaction.

2. Architecture at a glance

Outside reviewers open the CloudFront URL. The React app is served from a private S3 bucket and calls API Gateway. Two scheduled runs and the SLA timers come from EventBridge Scheduler. The send-guard writes the outbox in the same Postgres transaction as its safety checks. Only reply-graph and agent-run leave the VPC to call Sarvam or Gemini.

3. Golden Path mapped to services

At runtime, AI is called in Step 3 (Gemini picks from allowed actions), Step 5 (Sarvam hears and flags; Gemini structures unflagged replies) and optionally Step 7 (Gemini copilot brief). Every message a patient receives is an approved template.

Send-guard. Every outbound message calls send_guard(patient_id, template_id) inside the transaction that writes the outbox row. It rejects the send if consent is missing, agent messaging is off, the patient is paused or closed, a handover is open, or the template is not approved. The row lock (SELECT … FOR UPDATE) stops two workflows racing. HELP, ಸಹಾಯ and मदद are matched by string in channel-in before any model call.

5. AWS services

Public demo hosting (outside world)

  • S3 bucket (private, Block Public Access on) holds the built React/Vite app, rebuilt from the v7.2 screens. CloudFront serves it over HTTPS through Origin Access Control. The S3 website endpoint alone is HTTP-only and would need a public bucket, so it is not used.
  • Custom domain: demo.carepilot.<domain> and api.carepilot.<domain> via Route 53, with a free ACM certificate. The ACM certificate for CloudFront must be issued in us-east-1. This is the only resource outside Mumbai, and it holds no data.
  • Demo access: Cognito accounts for each role (coordinator, oncologist, chief, reviewer read-only), a permanent "synthetic data" banner, and a nightly reset-demo Lambda that reloads the synthetic register so every reviewer sees the same Golden Path story.
  • Protection: WAF managed rules and a rate limit on the webhook and the login. Turn WAF on before the URL is shared publicly.

6. Sarvam (purpose-specific) and Vertex AI (general LLM)

The split rule is simple: anything that hears, reads or speaks an Indian language goes to Sarvam, and anything that reasons over tokenised English goes to Gemini. Only Sarvam-30B decides the health-matter routing, as the MVP specifies.

Integration pattern

  • One AI client layer (shared Lambda layer) wraps both providers. It tokenises names, phone numbers, MRN and ABHA before any chat-model call. It applies a 20 s timeout with one retry, validates output with Pydantic and rejects extra keys, and logs model, prompt version, latency and tokens to ai_calls and the audit ledger (actor "AI suggestion").
  • Vertex AI access from AWS uses Workload Identity Federation: the Lambda's IAM role is exchanged for a short-lived Google service-account token, so no JSON key is stored. Use the asia-south1 regional endpoint (Gemini 2.5 Flash or a newer Flash listed there), never the global endpoint.
  • Prepaid governance: create a dedicated GCP project for CarePilot, set a per-day quota on the Vertex AI API, and add a budget alert on the prepaid balance.
  • Agent framework: LangGraph runs inside Lambda, with a PostgresSaver checkpointer on RDS so that a Gate 1–3 interrupt() can wait for days. Gemini is the only model bound to graph nodes. Sarvam is called as tools.

  • Identity: Cognito groups map to roles. The chief sees aggregates only, enforced in the API with Postgres row-level security as a second layer. Staff use MFA.
  • Encryption: KMS CMK for RDS, S3 and Secrets Manager. TLS 1.2+ everywhere. CloudFront OAC to a private bucket.
  • Least privilege: one IAM role per Lambda. Outbound traffic is HTTPS only. Only channel-out marks the outbox as sent. The GCP service account has roles/aiplatform.user only.
  • Cross-cloud data: Gemini receives tokenised English text only, never audio, documents or identifiers. Request and response logging is disabled for the Vertex project.
  • DPDP Act 2023: consent gates every outbound action. Purpose limitation is enforced through consent scope. Erasure follows a runbook, and the ledger keeps tokens, not identities.
  • Clinical AI exclusions: no diagnosis, severity or risk fields exist in any schema. The red-team eval set runs in CI.
  • Pilot: Saaras, Bulbul and Vision move to self-hosted deployments in the clinic's AWS account. Chat models stay on de-identified text.

Cost levers

  • Stop RDS and the NAT instance out of hours with an EventBridge schedule, which cuts about 60% off those lines. Keep the demo up during review windows.
  • Use Saaras speech-to-text-translate to avoid a second translate call for voice. Translate text replies only when a coordinator opens them.
  • Default to Gemini Flash. Use Pro only for the CI judge and, if needed, copilot briefs.
  • Run arm64 (Graviton) everywhere. Add no message bus, Aurora, OpenSearch or NAT Gateway in the sprint.
  • Set AWS Budgets alerts at US$50 and US$100, turn on Cost Anomaly Detection, put a Vertex AI daily quota and budget on the prepaid balance, and add a per-day Sarvam call cap that takes the safe path when hit.
  • Apply for AWS Activate credits and claim Sarvam signup credits, plus any Health-a-thon partner credits.

10. Build plan: stable core first, change at the edges

Build the closed loop without any AI first (Increments 0–3), then plug AI in at fixed points (Increments 4–5), then harden the demo for outside review (Increment 6). Most requirement changes then land in config, adapters or AI nodes, not in the core.

The flow that does not change: known patient → confirmed plan → order cards → gap detected → allowed action → approved message through the send-guard → reply (a button updates state; free text is routed to a person) → human decisions → next order card → named closure → resume. Every step is audited.

Rules that keep it stable while requirements move

  • Make the MVP's "How would you know the Golden Path works?" checklist an automated end-to-end suite. Add the relevant checks in each increment and run all of them on every change. A change that breaks one has touched the core.
  • Keep rules, templates, the autonomy policy and deadlines in versioned config from Increment 1, so most changes are data, not code.
  • Keep the AI behind one interface from Increment 4, so switching Sarvam ⇄ Gemini ⇄ self-hosted is configuration.
  • Triage each change request against the "Where expected changes land" table first. If it lands in the last row, it goes to clinical sign-off before it is scheduled.
